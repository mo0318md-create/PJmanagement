## 0. システム概要

プロジェクトを **プロジェクト > タスク > 子タスク** の3階層で管理し、
現在日・期間・ステータス・進捗率から「順調 / 遅延」を判定して可視化する **Google Apps Script の Web アプリ**。

| 項目 | 内容 |
|---|---|
| 想定利用者 | 社内 〜10名（管理者2名 / 担当者8名程度） |
| 想定データ量 | 〜50プロジェクト、1プロジェクトあたり10〜20タスク（合計 〜1,000行） |
| 実行基盤 | **Google Apps Script（Web アプリ）＋ スプレッドシート** |
| 認証 | Googleアカウント（`Session.getActiveUser()`） |
| 対応デバイス | PC（管理者中心）/ スマートフォン（担当者中心）。同じ画面がレスポンシブで変形する |
| 画面構成 | **1ページの Web アプリ**。画面の切替はブラウザ側で行い、サーバーへは行かない（§5） |

## 1. 用語定義

画面・モック・この要件書で同じ言葉を使う。「使わない言葉」は画面に出さない。

| 用語 | 定義 | 使わない言葉 |
|---|---|---|
| プロジェクト | 第1階層。テンプレートから生成される管理単位 | |
| タスク | プロジェクト配下の作業の**総称**（子タスクを含む）。第2階層だけを指すときは「親タスク」 | 課題、アイテム |
| 子タスク | 第3階層。タスク配下の具体的な作業 | |
| 種別 | タスクの種類：作業 / バグ / 要望（**固定の3種**） | 種別名としての「タスク」 |
| ステータス | 担当者が手で選ぶ区分：未着手 / 進行中 / 保留 / 完了 の**4つ固定**（完全版のようなプロジェクトごとの名前は持たない） | 分類 |
| 状態 | システムが自動で出す区分：**開始前 / 対応中 / 遅延 / 完了 / 期間未設定** の5つ。終了日とステータスだけで決まる（§3.3）。人は直接変えられない | 健全性、未開始、順調、注意 |
| 予定進捗率 | 期間に対する経過日数の割合（0〜100%） | |
| 実績進捗率 | 進み具合（0〜100%）。**末端は手入力、親は子の平均**（§3.2） | |
| 開始日・終了日 | 予定の期間（項目名） | 締切 |
| 期限 | 終了日の言い換え。**区分名だけ**に使う：今日期限・今週期限・期限順・期限まで | 期限切れ |
| 超過+N日 | 未完了のまま終了日を過ぎた日数 | N日遅れ |
| 担当者 | タスクを受け持つ人 | メンバー |
| ユーザー | ログインアカウント。設定画面でだけ使う | |
| 未アサイン | 担当者が決まっていないタスク | |
| ガント | 期間を横棒で並べた図。**全プロジェクト**・**1プロジェクト内**・**担当者別**・**個人ページ**の4か所 | タイムライン |

## 3. 進捗判定ロジック

### 3.1 予定進捗率

期間は**両端を含む日数**で数える。

```
総日数   = (終了日 - 開始日) + 1
経過日数 = (今日   - 開始日) + 1
予定進捗率 = clamp(経過日数 / 総日数, 0, 1)
```

### 3.2 実績進捗率（手入力・判定には使わない）

この％は**状態の判定には使わない**（§3.3）。「どこまで進んだか」を人が見るための数字。

| 対象 | 求め方 |
|---|---|
| 子タスクを持たないタスク | 担当者が入れた **進捗率（0〜100%）** をそのまま使う。未入力は 0% |
| 子タスクを持つタスク | **子の実績進捗率の単純平均**（自動。手入力できない） |
| プロジェクト | **配下のタスク（第2階層）の実績進捗率の単純平均**（自動） |

- ステータスを「完了」にしたら、進捗率は自動で 100% にする。
- 完了から戻したときは、100% のまま残す（担当者が直す）。

> 完全版では期間日数や作業の重さで重みを付けた加重平均だったが、
> 簡易版は**単純平均**とする。重みの設定・作業の重さの入力がどちらも無くなるため。
> 大小さまざまなタスクが混ざる親では実態とずれることがある点は、割り切りとして受け入れる。

### 3.3 状態の判定

上から順に評価し、最初に合致したものを採用する。**進捗率は使わない**。

| 順 | 条件 | 状態 | 色 |
|---|---|---|---|
| 1 | ステータス = 完了 | `done` 完了 | 青 |
| 2 | **今日 > 終了日（未完了）** | `delayed` 遅延 | 赤 |
| 3 | 開始日・終了日が無い | `no_period` 期間未設定 | 灰 |
| 4 | 今日 < 開始日 | `not_started` 開始前 | 灰 |
| 5 | 上記以外 | `on_track` 対応中 | 緑 |

**「順調」ではなく「対応中」と呼ぶ**：終了日だけで判定しているので、進み具合が良いかどうかは分からない。
「まだ終了日を過ぎていない」以上のことは言えないため、言い切らない名前にする。

**割り切り**：終了日が来るまでは、実態として遅れかけていても「対応中」のままになる。
遅れの兆しは、進捗バーに重なる縦線（予定進捗、F-2-7）と §3.2 の進捗率を、人が見て判断する。

> 完全版では「実績 − 予定」の差にしきい値（−10pt で注意、−25pt で遅延）を当てていた。
> 簡易版はこれを持たないため、**「注意」（黄色）が無く、しきい値の設定も無い**。
> 判定が進捗率の入力状況に左右されない代わりに、早期の兆しは出せない。

### 3.4 補足ルール

- **親の状態は親自身の終了日で判定する**（子の状態の最悪値を伝播させない）。
  ただし一覧では「配下の遅延件数」を併記し、親が順調でも中に遅延があることがわかるようにする。
- 保留は進捗率をそのまま使い、状態の判定は通常どおり行う。一覧では保留チップを別途表示する。
- 開始日・終了日が未設定のタスクは状態の判定対象外とし、「期間未設定」と表示する。

## 5. Google Apps Script での実装方針

### 5.1 全体の形

```
[ブラウザ] 1ページの Web アプリ（HTML + JS）
    │  google.script.run
    │    ① 起動直後  getSummary()  … projects + summary_cache + users（軽い）
    │    ② 続けて裏で getItems()   … items 全件（重い。画面はもう出ている）
    │    ③ 保存のたび saveItem() など（変更した行だけ）
    ▼
[GAS] doGet / getSummary / getItems / saveItem / …
    │  SpreadsheetApp
    ▼
[スプレッドシート] 1シート = 1テーブル（9シート）
```

| 方針 | 理由 |
|---|---|
| **画面は1ページ**。モックは画面ごとに別ファイルだが、実装では1つの HTML の中で表示を切り替える | GAS の `HtmlService` はページ遷移のたびに `doGet` が走り、毎回2〜4秒かかる。遷移のたびに待たせない |
| **2段階で読み込む**。まず集計キャッシュ（F-5-6）で一覧を出し、その裏でタスク全件を読む | プロジェクト一覧は50行だけ読めば描ける。1,000行のタスクを待たずに最初の画面が出る |
| **判定・集計・検索はすべてブラウザ側の JS で行う** | サーバー実行は6分制限があり、同時実行も詰まる。読み込んだ後はサーバーへ行かない。横断検索（F-5-10）も裏で読んだタスクに対してその場で走るので待ち時間ゼロ |
| **書き込みは変更した行だけ**（`setValues` で1行）。`LockService.getScriptLock()` で囲む | 全体書き戻しは遅く、同時編集で上書き事故が起きる |
| **書き込みのついでに集計キャッシュを更新する**。そのタスクが属するプロジェクトの1行だけ | 読むたびに1,000行を数え直さずに済む |
| **衝突の検知**は `updated_at` の比較で行い、「他の人が先に更新しています。再読込してください」と出す | 10名規模ならこれで足りる。行ロックまでは作らない |
| 認証は `Session.getActiveUser().getEmail()` を `users` シートと照合 | GAS の標準機能で済む |

裏での読み込みが終わるまでは、横断検索・マイタスク・担当者一覧に「読み込み中」を出す。
プロジェクト一覧とプロジェクト概要は、集計キャッシュだけで先に描ける。

### 5.2 シートの決まり

- 1行目を列名のヘッダー行にし、コードは**列名で引く**（列の順番に依存しない）。
- 主キーは文字列の UUID（`Utilities.getUuid()`）。
- 日付は `yyyy-MM-dd` の文字列で持つ（タイムゾーンのずれを避けるため、日付型にしない）。
- JSON を入れる列（`custom_fields` など）は文字列として保存し、読み込み時に `JSON.parse`。

### 5.3 判定ロジックの置き場所

§3 の計算は**引数だけで答えが決まる純粋な関数**として1ファイルにまとめる。
ブラウザ側で動かすほか、集計キャッシュの更新（§5.1）とお知らせの生成（§5.4）でサーバー側からも呼ぶ。
同じ判定が2か所で食い違わないよう、コードは1つにする。

### 5.4 お知らせの作り方（F-5-9）

| 種類 | いつ作るか |
|---|---|
| 担当になった／外れた | 担当者を変えて保存したとき、その場で作る |
| 期限の前日と当日 | **毎朝の時間主導トリガー**（`ScriptApp.newTrigger` で 7:00 頃）でタスクを走査して作る |
| 遅延になった | 同じ朝のトリガー。前日は遅延でなかったタスクが遅延になったときだけ作る |

- 朝のトリガーは1,000行の走査と書き込みで、6分の実行制限には十分収まる。
- 既読フラグは `notifications` シートの行を更新する。
- 90日より古いお知らせは、同じトリガーで削除する（行が際限なく増えないように）。

## 6. 非機能要件

| 項目 | 目標 |
|---|---|
| 初回読み込み | プロジェクト一覧が出るまで**2秒以内**（集計キャッシュのみ）。タスク全件の裏読みは追加で5秒以内 |
| 画面の切替・横断検索 | 即座（サーバーへ行かないため） |
| 保存 | 2秒以内 |
| 同時利用 | 5名程度の同時操作で破綻しないこと |
| データ保全 | スプレッドシートの版履歴に依存。日次でコピーをバックアップ |
| ブラウザ | Chrome / Edge の最新版 |
| 表示 | レスポンシブ（375px 〜 1920px）、ライト/ダークモード対応 |
